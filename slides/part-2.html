Testing14:50

The spec is the test oracle

  • Tests come from the use case, not from the code: one test per scenario, flow and business rule
  • A test that disagrees with the code stays red. The agent does not bend the test to the code
  • Integration layer first: a Browserless view test runs against the real service and database
  • Browser tests for the journeys across use cases
@UseCase(id = "UC-001",
         scenario = "A2: no room available",
         businessRules = {"BR-002"})
@Test
void showsMessageWhenNothingIsFree() {
    // …
}

The annotation makes the test traceable: requirement → use case → business rule → code → test.

Change15:40

When requirements change

  • Change the spec first: the use case or the business rule, not the code
  • Update the code from the spec, do not hand-patch
  • Let the tests show the impact: failing tests point to code that no longer matches
  • Review spec and code together: one pull request with both diffs
  • Check the coverage again: where do code and spec drift apart?
Change15:43

Before or after implementation?

Change before implementation

The use case is specified, no code exists yet.

/requirements→/spec-review→/use-case-spec→/spec-review
  • Update the FR first, then the use cases that realize it
  • /spec-review impact analysis: “what does FR-014 affect?”
  • Cheapest moment for a change: only text moves

Correction after implementation

Code and tests exist. The behavior is wrong or the rule changed.

/use-case-spec→/use-case-implement→/use-case-test→/use-case-coverage
  • Correct the use case first, never only the code
  • Failing tests show where code no longer matches
  • Coverage check proves spec and code match again

Lab 7 is the right-hand case.

Change15:46

New feature or correction?

The requestWhat it becomesSkills
A new user goal
“Guests can leave a review after checkout”		A new use case with a new UC id, traced to a new FR
/requirements→/use-case-diagram→/use-case-spec→ …
A new way to reach an existing goal
“Reserve by phone through the receptionist”		A new alternative flow, e.g. 3a, in the existing use case
/use-case-spec UC-###→/use-case-implement→ …
The system does it wrong
“A stay is at most 14 nights”		A corrected step or business rule. Same UC, same id
/use-case-spec UC-###→/use-case-implement→ …

Rule of thumb: if the actor's goal changes, it is a new use case. If only the path or a rule changes, edit the existing one. Existing tests stay green for a feature and fail first for a correction.

Token economy16:40

Input tokens drive the cost

Context per turn × number of turns. The whole history is sent again with every turn, and letting the agent search the repository burns tokens fast. Output is the small part.

Measure cost per use case

Take a baseline from spec to test. It should fall as specs and structure improve. What are your numbers from today?

Levers

  • One use case per session, then close it
  • Point to files instead of letting it search
  • Keep specs short and focused
  • Keep the prompt cache: do not switch model or MCPs mid-session
  • Cheap models for boilerplate, strong models for design and review
  • Subagents keep the main context clean
Token economy16:45

Subscription or API?

Subscription seats

  • Predictable cost, good for daily development work
  • What you used today

API billing

  • Pay per token, needed for automation and pipelines
  • The Werkstatt on day 2 runs on API keys, with a budget per use case
  • Who pays: the customer can provide the keys, which also helps with data protection
  • Set a budget: cost per developer per month is easier to defend than cost per prompt
