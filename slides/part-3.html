06 · BROWNFIELD

From code back to the spec

Most systems already exist. They have code, but no specification.

Brownfield10:10

Brownfield workflow

The agent readsCode, database schema, tests and old documents of the existing system.
The agent writes the spec/reverse-engineer generates the use case diagram, the use cases and the entity model.
Humans review, then spec-firstThe code shows what the system does, not what it should do. From here, every change starts in the spec.
Brownfield10:14

Five steps to a baseline

1
/stack

Detects layers and modules from the build files and the source tree

2
/reverse-engineer, one module at a time

Use case diagram, one spec per use case, entity model from the database

3
Human review with the business

The code shows what the system does, not what it should do. Bugs become open questions

4
/open-questions and /spec-review

Gaps recorded, contradictions found, then the specs are the baseline

5
Continue with yesterday's workflow

Every change from now on: change, correction or new feature

Large codebases

  • The agent sees only what fits in its context
  • Reverse engineer per module, not the whole system at once
  • A modular structure keeps the context small: one module, its use cases, its entities
  • No clear modules yet? Make cutting them part of the modernization
  • Start with the module you will change next
Brownfield10:19

What the code cannot tell you

The agent can recover

  • Actors from roles and security config
  • Goals from views, controllers, endpoints
  • Steps and alternative flows from the control flow
  • Rules from validators, constraints, ifs
  • Entities and relations from the schema

Only people can decide

  • Is this behavior intended, or a bug?
  • Is this feature still used?
  • Why does this rule exist?
  • Which naming is the business language?

Each answer goes into the spec, not into a chat.

A reverse-engineered spec is a draft. It becomes the baseline after the review.

PetClinic11:13

Hooks guard the session

HookWhat it doesEvent
require-sensors.shRefuses to end a turn while src/, docs/ or pom.xml changed after the last green sensor runStop
guard-spec-status.shRefuses an edit that sets Done, Tested or Automated without a coverage audit in this sessionPreToolUse
check-spec-status.shRereads every Status: after each tool call, so sed and heredocs are caught tooPostToolUse
record-coverage-check.shRecords that the coverage agent finished: the evidence the guards ask forSubagentStop
record-sensor-run.shMarks a sensor run only if every Surefire report is fresh and greenPostToolUse
session-start.shRecords the starting commit and every Status: lineSessionStart

Guards read the repository, not the tool call. Evidence is positive: a fresh report counts, a quiet console does not. Fail open: a broken hook never blocks the session.

Rule: if it can be checked by reading the repository, it is a test, not a hook. Hooks only fire in a Claude Code session; ArchUnit binds CI and every contributor.

PetClinic11:17

SonarQube as a sensor

In CI

  • mvn verify sonar:sonar on every push and pull request
  • Coverage: JaCoCo of Browserless and Playwright tests, merged
  • Generated jOOQ code excluded
  • The quality gate blocks the merge
  • The hook smoke test runs before the build

For the agent

  • SonarQube MCP server: the agent reads issues, hotspots, the gate status
  • SonarQube plugin for Claude Code: /sonar-list-issues, /sonar-fix-issue, /sonar-quality-gate
  • SonarQube for IDE as the fast local loop

From a report for humans to feedback for the agent.

Guardrails12:00

Turn guidelines into guardrails

  • If a rule matters, enforce it: a rule in CLAUDE.md is a wish, a failing build is a fact
  • Architecture rules as tests: ArchUnit checks layers, packages and dependencies
  • Hooks for the session: what the agent must have done before it says “done”
  • Quality gates in CI: static analysis, dependency check, coverage
  • A mistake twice is a gap in the harness
@ArchTest
static final ArchRule uiDoesNotUseJooq =
    noClasses().that().resideInAPackage("..ui..")
        .should().dependOnClassesThat()
        .resideInAPackage("org.jooq..");
#!/usr/bin/env bash
# Stop hook: no end of turn while tests are red
active=$(jq -r .stop_hook_active)
[ "$active" = true ] && exit 0  # no loop
./mvnw -q test > target/hook.log 2>&1 && exit 0
echo "Tests are red, fix them:" >&2
tail -30 target/hook.log >&2
exit 2  # blocks, stderr goes to the agent

Harden the harness

Track A · HRS

  • /architecture-decision for a decision the plugins made for you, e.g. views never use jOOQ directly
  • Add com.tngtech.archunit:archunit-junit5 (test scope) to the POM by hand. archunit.version is already there
  • Let the agent turn the ADR into an ArchUnit rule
  • Stop hook in .claude/settings.json that runs ./mvnw -q test

Track B · Your project

  • /architecture-decision for a rule your team already follows but nobody checks
  • Enforce it with your stack's tool: ArchUnit, NetArchTest, dependency-cruiser, ESLint boundaries
  • Stop hook that runs your fastest test command
  • CLAUDE.md that links requirements, architecture and the stack file

Done when: breaking the rule on purpose makes the build red, and the hook stops the agent once while the tests are red. Bonus: a @UseCase traceability test like the PetClinic's, or a SonarQube quality gate.

08 · THE WERKSTATT

A software factory

From approved use case to tested pull request, without steering every step.

Werkstatt12:25

First by hand: one team, shared decisions

1Spec reviewed/spec-review green
→
2Owner assignedOne developer per UC
→
3Branch or worktreeIsolated session
→
4Agent implementsCode and tests
→
5Quality gatesBuild, ArchUnit, tests
→
6Review vs. specCoverage audit
→
7MergeStatus Implemented
  • Shared harness: same CLAUDE.md, plugins and skills for everybody, from the repository
  • Two agents never work on the same specification. Small pull requests that can be reviewed
  • Progress is tracked per use case on a Kanban board, not in story points

Steps 3 to 6 are always the same. That is what the Werkstatt automates.

Roles and branch model

A workshop, not a factory floor: the domain expert and the software engineer stay in it.

  • Verified audit: “complete” is checked: a matrix row per step, flow and rule, and a Read of every cited file in the tool log
  • Outcomes: ready, blocked, stuck, pending, skipped
Werkstatt12:36

The andon cord

When a station finds a gap in the specification, it does not guess.

  • It records a question in docs/open_questions.md with **Blocking:** Yes
  • The Werkstatt reads the file, not the agent's answer
  • The use case stops: only the question goes into the pull request
  • The domain expert answers it in the change branch, the next run builds again

Why this matters

The main difference from code-first agent pipelines: a gap becomes a question for a person, not a hidden assumption in the code.

Where it runs

  • GitHub Actions: reusable workflow aiup-werkstatt.yml, a throwaway runner
  • Locally: pipelines/werkstatt/run-local.sh, in a separate worktree, no PR

09 · PRACTICE

Lessons from customer projects

What changes when a team works like this every day.

Practice12:45

Two bottlenecks

Requirements and context

  • The agent builds faster than the business can decide what it wants
  • Unclear requirements give plausible but wrong code
  • Large legacy code does not fit. The agent sees only what you give it

Review

  • Generating is fast, understanding is not
  • Without a spec you review against nothing
  • Review must be risk-based: deep review where a mistake hurts, sensors for the rest
  • Plan the review time. Teams underestimate it every time
Practice12:47

Impact on the architecture

Context is the first bottleneck: the agent sees only what fits, and every file in the context is paid for again in every turn.

Modular architecture

→ Self-contained systems

  • One system, its use cases, its entities: a small context per task
  • No modules yet? Cutting them is part of the modernization

One ecosystem

→ Full-stack frameworks

  • One language, one build, one test stack, e.g. Vaadin or Hilla
  • One set of guardrails covers everything: ArchUnit, one test runner

Harnessable code

→ Easy to check

  • Strong types: the compiler is the first sensor
  • Clear module boundaries a rule can enforce, known frameworks

Teams get smaller: 1–2 developers per self-contained system, Kanban, progress per use case. Architecture is now also a cost decision.

Practice12:49

Risk-based review at Anthropic

  1. 1
    Before the PRAgent runs build, tests, linter. A subagent reviews the diff in a fresh context
  2. 2
    AI review on every PRParallel agents hunt bugs, verifiers vote. Only confirmed findings are posted
  3. 3
    Security reviewSeparate pass. Open findings block the merge
  4. 4
    CI and merge queueLint, types, tests, build. Re-run against the latest main
  5. 5
    Human approval by riskThe change sets the tier, not the author

Human approvals by risk

0Low docs, additive change behind a flag
1Medium ordinary product change
2High billing, CI workflows, auto-updater

What stays human

  • Should we build this at all?
  • Architecture decisions
  • Reading the evidence
  • Owning the outcome

Risks12:51

Risks and how to handle them

RiskMitigation
Plausible but wrong code, silent logic errorsSpec as oracle, tests per business rule, coverage check
Architecture driftArchUnit, stack plugin, ADRs written before the first use case
Prompt injection, over-permissive agentsSandbox or VM, minimal permissions, review dependencies
Data leakageNo production data, self-hosted models for sensitive code
Spec driftOne owner per use case, spec diff in the same pull request, traceability sensors
Legal and IP: license, ownership, auditabilityDependency and license scans, every change traced to a use case
Skill erosion, false confidenceReview everything; “AI created it” is not a quality gate
Practice12:53

Harness engineering in practice

  • Start small: one CLAUDE.md, one skill, one quality gate
  • A mistake twice is a gap in the harness: fix the context or add a check, not only the code
  • Behavior is the weakest harness: specs and test cases fill the gap
  • Share it like code: versioned and reviewed, one harness for the team
  • Measure: first-pass rate of the Werkstatt, review findings, tokens per use case

Try it on your own stack

  • Pick one real use case: small, but with real business rules
  • Write the spec first: vision, requirements, entity model, one use case. Or /reverse-engineer one module
